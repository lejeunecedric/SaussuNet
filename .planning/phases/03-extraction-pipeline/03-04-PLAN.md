# Plan 03-04: Source drift & sha256 no-op (PIPE-02)

## Objective
Make re-submission cheap and honest: unchanged source → provable no-op (no tokens burned, no log churn); changed source → loud drift entry + re-ingest through the merge path. This is ROADMAP success criterion 2.

## Context
- D-08 locked: drift = same URL, sha256 changed → auto re-ingest + log.md drift entry + pages updated via normal merge path; sha256 match = no-op; state in the existing `sync_state` table (03-03's migration 0007 added the `sha256` column; `set_source_sha256`/`get_source_sha256` exist).
- 03-01's `ingest_url` already writes sha256 after fetch — this plan inserts the comparison BEFORE `write_raw`/extraction and adds the drift log.
- Pitfall 1 (source drift) warning signs to respect: no repeated identical ingest entries in log.md; token spend drops to zero on unchanged re-submits — the MockProvider `call_count()` assertion is the CI proof of exactly that.
- D-17 tie-in: entity_sources uses INSERT OR IGNORE on (canonical, source_id) — a drift re-ingest of the same URL cannot add a second source row. Prove it here end-to-end.
- `vault::log::append_entry` handles rotation (~500 entries → log-YYYY.md) — do not hand-roll log writes.

<threat_model>
- **SSRF (D-01/D-03):** unchanged — fetch stays behind plan 03-01's `assert_public_http_url` (scheme allowlist, private/link-local/loopback/CGNAT ranges, per-hop redirect re-check). No new network surface.
- **Uploaded-PDF guards:** N/A here — drift logic is ingest_url-only; uploaded PDFs are exempt by D-04 (03-05 owns upload guards).
- **No secrets in logs (Phase 2 D-03 pattern):** the drift log.md entry carries source URL + old/new sha256 only — never page content, never query-string secrets beyond the URL the user themselves submitted; log.md is vault content and already user-visible.
- **Prompt injection:** unchanged backstop — no-op path performs NO LLM call at all (strongest possible bound); re-ingest path uses 03-03's untrusted-data prompts and the write_page funnel (PIPE-06, 03-06) — the LLM never writes disk directly.
- **Validator bypass:** the only writes here are `vault::raw::write_raw` (raw overwrite), `vault::log::append_entry`, and the existing `write_page` funnel — no new disk paths.
</threat_model>
