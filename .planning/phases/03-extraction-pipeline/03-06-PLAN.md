# Plan 03-06: Deterministic write-path validator (PIPE-06)

## Objective
Close the trust gap: nothing an LLM composed reaches the vault unless deterministic Rust vouches for it first. Link whitelist, frontmatter schema, and provenance presence/validity are checked BEFORE any disk write; wiki-as-source self-citation is rejected. This is ROADMAP success criterion 5.

## Context
- PIPE-06 locked: every generated page passes the deterministic write-path validator before reaching disk; the LLM never writes directly. D-11: the validator enforces provenance-marker presence and valid `raw/` targets.
- Hook decision (Claude's Discretion, recorded): wrapper `write_generated_page` in `vault/writer.rs` calling new `vault::validate` then `write_page`. Rationale: keeping the check inside the `vault/` module family preserves "writer is the sole author" (VLET-02) while keeping plain `write_page` usable for human/CLI paths that must not require provenance.
- Existing pieces: `frontmatter::validate_page` (schema + taxonomy) already runs inside write_page — the validator reuses `frontmatter::parse`/`validate_page` for its own frontmatter gate and adds the generated-page-specific rules. `index.md` format: entries are `- [[{stem}]] — {title}` lines written by `index::upsert_entry` (see vault/index.rs:63) — parse stems from the `- [[stem]]` prefix. `list_entities` gives canonical names + page_paths.
- Provenance marker regex: `\^\[raw/[^\]]+\]` (superscript-caret form, D-07). Wikilink scan: reuse `frontmatter::count_outbound_wikilinks` machinery or a small `pulldown-cmark`-free regex over `[[target|alias]]` → target (strip alias after `|`, strip `#` heading anchors).
- Pitfall 4: reject `sources:` entries (and provenance targets pointing OUTSIDE raw/ by construction of the regex) whose source path resolves inside the wiki layer; also reject a `sources` entry that is not under `raw/` at all.

<threat_model>
- **SSRF (D-01/D-03):** N/A — no network in this plan; fetch guard from 03-01 unchanged.
- **Uploaded-PDF guards:** N/A here (03-05); the validator treats PDF-derived pages like any generated page (provenance must point at the raw .md/.pdf record).
- **No secrets in logs (Phase 2 D-03 pattern):** validation rejections log rel_path + rule name only, never the full page body (a poisoned page may contain attacker text).
- **Prompt injection (primary defense here):** this validator is the deterministic backstop for a poisoned LLM output — a hijacked pass-2 can only express: whitelisted links, schema-valid frontmatter, and provenance to real raw/ files. It cannot introduce dangling authority (new uncited claims lack markers → rejected), cannot cite wiki pages as sources (self-citation loop closed), cannot write anywhere except through write_page's path guard. Prompts (03-03) wrap untrusted data; the validator bounds the damage.
- **Validator bypass (the threat this plan exists for):** acceptance greps prove the only pipeline write path is `write_generated_page`; `write_page` remains the sole disk-mutating entry (VLET-02 unchanged); no fs writes in validate.rs (pure function over strings + read-only FS reads of index.md/raw existence).
</threat_model>
