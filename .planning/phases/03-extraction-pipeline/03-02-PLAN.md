# Plan 03-02: POST /ingest — HTTP entry under the configurable base path

## Objective
The user-facing door for the whole phase: `POST {base}/ingest` on the daemon accepts a URL, inserts the durable job that plan 03-01's worker drains, and returns the job id. axum lives in the binary crate only; the base path is configurable from day one (D-13) so Phase 5's UI extends the same server.

## Context
- D-01 locked: HTTP entry point on the daemon, axum in the binary crate only, returns the job id; CLI submitter deferred (Phase 5 supersedes).
- D-13 locked: base-path-aware from day one, nested under the configurable base path (`/saussunet` per PROJECT.md).
- Existing wiring: `main.rs::boot()` already does config → `boot_open` → provider → `spawn_workers` → ctrl_c. The axum serve task joins that select as a third long-lived task.
- Config coupling warning: `lib.rs::default_config()` and the committed root `config.example.toml` are pinned byte-identical by a Phase 1 test — edit BOTH in the same commit or `committed_example_config_matches_default_config` fails.
- `ServerSection` currently has only `bind` (default `127.0.0.1:8080`). Follow the `VaultSection` triad pattern: `#[serde(default)]` field on FileConfig + `#[serde(default = "...")]` per field + manual `Default` impl.

<threat_model>
- **SSRF (D-01/D-03):** the endpoint does NOT fetch — it only validates and enqueues (fetch happens in the worker at execution time, plan 03-01). Submit-time validation still calls core `pipeline::fetch::assert_public_http_url` so obviously-blocked URLs fail fast with 400; the authoritative guard remains in the fetch path (defense in depth — a job row could be inserted by other means).
- **Uploaded-PDF guards:** N/A in this plan (upload route lands in 03-05 on this same router; size cap + content-type + filename-slug rules defined there).
- **No secrets in logs (Phase 2 D-03 pattern):** request/response logging carries method, path, status, job id only. Never log full bodies (a future upload route must not log bytes); no api_key anywhere in this crate.
- **Prompt injection:** the endpoint never talks to the LLM; it writes only a job row. Untrusted content reaches the LLM only via the worker (03-03 prompts wrap it as data); the validator + write_page funnel (PIPE-06, 03-06) is the backstop — the LLM never writes disk directly.
- **Validator bypass:** the HTTP layer performs zero vault writes — its only side effect is `insert_job`. All page mutation stays funneled through `vault::writer::write_page`.
- **Body size:** JSON body limited via `tower_http::limit`/`DefaultBodyLimit` (64 KiB) — this endpoint accepts only a URL string.
</threat_model>
