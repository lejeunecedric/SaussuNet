# Plan 04-07: opportunistic RFC 6578 sync-collection (pageTokens)

## Objective
Sources whose servers support collection-sync get cheap delta polls (changed + removed items only, one token per source); servers that don't are latched to the plain PROPFIND walk forever after. This completes SRCC-02's "pageTokens" persistence claim.

## Context
- `dav.rs` addition (exact):
  ```rust
  pub struct SyncReport { pub entries: Vec<DavEntry>, pub token: Option<String> }
  /// POST-as-REPORT (RFC 6578): Depth: 0, body:
  /// <d:sync-collection xmlns:d="DAV:"><d:sync-token>TOK or empty</d:sync-token>
  ///   <d:sync-level>infinity</d:sync-level><d:prop><d:getetag/><d:getcontentlength/></d:prop></d:sync-collection>
  /// 207 → parse via 04-03 parser (per-item status: 200 = added/changed, 404 = removed)
  ///       + extract_sync_token; token longer than 4096 chars ⇒ Err (opaque-string cap).
  /// Any non-207 → Err (caller decides stale-retry vs latch).
  pub async fn sync_collection(&self, rel: &str, token: Option<&str>) -> Result<SyncReport>
  ```
- `poll_once` branch (before the BFS walk): read `get_sync_state(vault_id, source_id)`. If `sync_unsupported != true`: attempt `sync_collection("", stored_token)`. On Err with `stored_token.is_some()` ⇒ retry once with `None` (stale token — Pitfall 5). On Err with empty token ⇒ `set_sync_unsupported(true)` and fall through to the walk (this poll AND all future ones). On Ok ⇒ entries with status 200 map to Added/Changed candidates (ext-allowlist + sha256 gate + submit + row upsert — reuse the 04-05 delta-application code path; walk-set semantics do NOT apply: a sync delta is not a complete universe, so NO diff-based removals — removals come only from 404-status items); entries with status 404 ⇒ removal handling (log + delete_watch_row); persist token via `set_sync_token` (only on success). Then `record_sync_poll` as before. The PROPFIND fallback path is byte-for-byte the 04-05 walk.
- Stub additions: `StubHandle::set_sync_mode(SyncMode)` where `SyncMode::Unsupported` (default — POST ⇒ 400), `SyncMode::Enabled { script: Vec<SyncReply> }` with `SyncReply { items: Vec<(path, ItemStatus)>, token: String }` served in order (last reply repeats); POST bodies already land in the request log — tests assert on recorded bodies for token round-trip.
- Test fixtures: sync-capable source A (`sync_token_persisted_and_reused`): reply 1 = `{items: [(note.md, 200)], token: "http://stub/sync/1"}` → poll ⇒ job + `sync_state.token == "http://stub/sync/1"`; reply 2 = `{items: [(gone.md, 404)], token: "http://stub/sync/2"}` → poll ⇒ removal log + row gone + token advanced; assert second poll's POST body contains `http://stub/sync/1`. Source B (`sync_unsupported_falls_back_forever`): POST always 400 ⇒ after first poll `get_sync_state.sync_unsupported == true`, request log shows exactly one POST ever, PROPFIND ingestion still works on poll 2. Stale-token test (`stale_token_resyncs_not_latches`): mode replies 400 for token "old" then 207 for empty ⇒ sync_unsupported stays false, one 207 poll completes.

<threat_model>
- **HIGH — untrusted sync responses:** report bodies pass the same 8 MiB cap + roxmltree no-DTD parse as PROPFIND (04-03/04-04 controls reused verbatim); the returned token is treated as an OPAQUE string — size-capped at 4096 chars, stored parameter-bound (sqlx), never interpolated into a URL or command; a token that fails to round-trip just yields a 400 → stale-retry path (no injection sink exists).
- **HIGH — credential leakage:** sync_collection errors carry the same sanitized scheme+host+path strings as propfind (shared error helper — do not fork a new error format).
- **DoS (token churn / delta storms):** stale-token retry is bounded to ONE retry per poll; a malicious server flooding Changed items is absorbed by the sha256 gate (no enqueue without content change) and the queue's bounded worker pool.
- **Removal integrity:** sync deltas never trigger diff-based mass removals (delta ≠ complete universe) — only explicit 404 items remove state. Partial-failure storms impossible by construction.
- SSRF / prompt injection: N/A new surface — same trusted server, same pipeline funnel (Phase 3).
</threat_model>
