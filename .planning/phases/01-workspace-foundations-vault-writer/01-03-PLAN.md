<objective>
Human-edit protection via per-section gen_hash three-way merge: the writer records section hashes from the first write, and on every subsequent write compares the current on-disk file against its own recorded hashes — match → overwrite (agent-only edits), mismatch → human edited → skip + record conflict + log (D-06), protected → refuse (D-07), no-gen_hash in wiki layer → human-owned refuse (D-08). Makes ROADMAP SC3 TRUE and produces the `pending_proposals` rows the Phase 5 review queue consumes.

Purpose: Pitfall 7 — the hash must exist from day one; you can never retroactively know what the user changed. This is the phase's hardest logic and the product's trust mechanism.
Output: `vault/ghash.rs`, three-way check in `write_page`, conflict recording path, `conflicts` CLI subcommand, integration tests including the edit-then-regenerate scenario from PITFALLS "Looks Done But Isn't".

Refines Plan 01-02's writer slice (same write path, now merge-aware) — not a separate layer.
</objective>

<threat_model>
ASVS L1 surface for this plan:
- **Protection bypass (T-03-01):** The gen_hash/protected/human-owned checks must live inside `write_page` under the write lock — no CLI or store path may write a vault file without passing them. The `write-page` CLI is a thin caller; there is no "force" escape hatch in Phase 1 (a force flag would be the bypass).
- **Conflict payload handling (T-03-02):** `proposed_content` is arbitrary text stored in SQLite — inserted only via parameterized binds, never interpolated into SQL, never executed or written to disk by the recording path itself.
- **Log forging via title/path (T-03-03):** conflict log entries reuse Plan 02's sanitizer; a page title containing `## [` or newlines cannot forge log entries.
- **Hash confusion (T-03-04):** frontmatter is hashed separately from section bodies (D-05) so a frontmatter-only change (e.g. human adds `protected: true`) is detectable and does not invalidate section hashes; the `gen_hash` map is stripped before hashing its own frontmatter on BOTH write and check sides (canonical serialization, stable key order) so the stored map never hashes itself — write-side and check-side values are comparable; section hashes are computed over exact bytes of the section including its heading line, so whitespace-only human edits are still detected.
- **DoS on SQLite (T-03-05):** conflict rows are bounded by real write attempts (single writer, serialized); no unbounded growth vector in Phase 1 (no automated regeneration loop yet).
</threat_model>

Slug = kebab-case of heading text (lowercase, non-alphanumeric runs → single hyphen, trim hyphens). `pub fn section_hashes(body: &str) -> BTreeMap<String, String>` — sha256 hex of each section's exact bytes (heading line through the line before the next `## `, trailing newline included). `pub fn frontmatter_hash(fm_value: &serde_yml::yaml::Yaml) -> String` — **computed over the frontmatter YAML with the `gen_hash` key REMOVED**, re-serialized canonically (stable key order — sort keys via BTreeMap — fixed flow style/indent) then sha256 hex. This exclusion is mandatory on BOTH sides: the write path hashes the new content's frontmatter BEFORE the gen_hash map is inserted, while the check path reads the on-disk frontmatter WITH the map already present — without stripping `gen_hash` the two values can never match and every regeneration would falsely route to conflict (D-05: "the frontmatter itself is hashed separately from section bodies" — separately means the map excludes itself). Stored under reserved key `__frontmatter__` in the same map. `pub fn compute_map(fm_yaml: &str, body: &str) -> BTreeMap<String,String>` — parse fm_yaml, remove `gen_hash`, canonicalize + hash → section_hashes + `__frontmatter__`; used identically on the write side (over the new content) and the check side (over the on-disk file). `pub fn human_edited(stored: &BTreeMap<String,String>, current: &BTreeMap<String,String>) -> bool` — true iff any key present in stored has a different value in current (new sections the agent adds are NOT human edits; missing/changed stored sections are).
  **writer.rs three-way check** — extend `write_page` between validation and the atomic write, still under the write lock. Read the existing file if present, split its frontmatter/body:

  - Case clean-overwrite: no existing file (first write) OR gen_hash present and no human edits → proceed; before serializing, set `fm.gen_hash = Some(ghash::compute_map(fm_yaml_of_new_content, new_body))` — recorded from the FIRST write (Pitfall 7).
